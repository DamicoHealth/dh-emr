Admin guide

This guide is for the person who runs DH EMR for an organization: the org lead. It covers everything only an admin can do. For everyday charting, read the user guide. For setting up a single device for the first time, read Getting started.

1. What an admin can do

DH EMR has two kinds of admin, depending on your organization's mode:

  • Field mode: the admin is a device. The setup wizard asks "What is this device allowed to do?" with two choices: "Enter and view records (most devices)" and "Also change the form and clinic settings for everyone". Most devices should be standard. Keep one or two admin devices with the people who run the clinic.
  • Clinic mode: the admin is an account. The first admin account is created during cloud setup (see below). After that, admins make other admins on the Staff tab.

Only an admin can change:

  • Clinic lists: sites, clinicians, complaints, procedures, referral destinations, and the patient flow stations
  • The formulary and the lab test panel, including reference ranges
  • Diagnosis quick-picks and prescription presets
  • Form templates, in the template editor
  • The organization's mode (clinic mode: administrator accounts only)
  • Staff accounts (clinic mode, on the Staff tab)

On a standard device, none of this is hidden. The controls are visible but turned off, and the reason is written right there: "Only an admin device can change this. This device is set to standard." The template editor opens read-only with the same reason. This is deliberate: a clinician can always see what exists and knows who to ask.

There is no button in the app to change a device's admin role after setup. On a cloud-connected organization, the role stored in the cloud's device list is what counts: change a device's role there (the devices table in your Supabase project) and the device adopts it on its next sync. On an offline-only device, the choice made in the wizard stands, so choose carefully.

2. Standing up your cloud project

Your records live on your devices and, if you want sync, in a Supabase project that your organization owns. Damico Health hosts nothing and sees nothing.

The full step-by-step lives in SETUP.md, in the supabase folder of the DH EMR source code, next to setup.sql and verify.sql. It takes about fifteen minutes and needs no command line. In short:

  1. Create the project. On supabase.com, create a new project. Pick the region closest to the clinic. Store the database password in a password manager; it is rarely needed again.
  2. Run the schema. Open the SQL Editor, paste the entire contents of setup.sql, and run it. It is safe to run twice; re-running is the documented upgrade path.
  3. Verify. Paste and run verify.sql. Every row of its output must say PASS. It changes nothing; it ends by rolling itself back.
  4. Get the app credentials. The Project URL is under Project Settings, then Data API. The publishable key (sb_publishable_...) is under Project Settings, then API Keys. Those two values are what every device enters.

The key rule. Devices get the Publishable key, or the legacy anon key, and nothing else. Never put the sb_secret_... key or a legacy service_role key on any device, in any chat, or in the app. It bypasses every security rule. The app refuses keys that look like it, on purpose: "Use the Publishable key, or the legacy anon key. NEVER a Secret or service_role key: those bypass every security rule and this app refuses them."

Field mode organizations are done here. Enter the URL and key on each device (in the setup wizard, or under Settings in the Cloud sync card), save one test visit, tap the sync chip, and check that one row appears in the project's Table Editor under records. Then delete the test visit in the app, not in the dashboard: deleting in the app marks the record deleted everywhere, and rows are never hard-deleted by design.

Clinic mode needs a few more steps, all in SETUP.md section 4:

  • Enable the Email sign-in provider, and turn OFF "Confirm email". Without your own mail server, confirmation emails to staff mostly never arrive and accounts strand half-created. Admin approval inside the app replaces what confirmation was for.
  • Create the org lead's account from the dashboard (create the user directly with a password; do not use "Send invitation", which relies on the same restricted mailer).
  • Make that first account the administrator with the one SQL line printed in SETUP.md section 4. This is deliberate: signing up never grants any access by itself, because anyone in the world who obtains the project URL and publishable key can sign up. The first admin must be minted by hand.
  • Do not rely on email password resets. If a password is lost, the fix is a fresh account; SETUP.md has the recovery playbook.

If your organization runs seasonal missions, read the free-tier pausing section of SETUP.md. Supabase pauses free projects after about a week of no traffic, and a project paused long enough can stop being restorable. Either pay for the project, or open the dashboard monthly, and always keep device backups. The backup file is the true archive; the cloud is a convenience copy for the devices, not the organization's only copy.

3. Field mode or clinic mode

The app describes the two modes like this, in the Organization card under Settings:

  • "Clinic mode: every staff member signs in with their own account, an admin approves each account, and visits carry who recorded them."
  • "Field mode: devices share the project key and work offline-first. Anyone holding the key can read and write, so the key is the whole fence."

Choose honestly, based on what each gives up:

  • Field mode gives up accountability and access control. The database cannot tell devices apart. Anyone holding the key can read every record. Revoking a device stops an honest device, not a determined person who still has the key. If someone leaves on bad terms, the key they carry still works. Clinic mode is the fix.
  • Clinic mode gives up some offline independence. Signing in needs a working connection, and a device that cannot reach the server for over a week shows a banner: "Reconnect to confirm your account." Everything keeps working in the meantime, but the account must be confirmed eventually. Every new account also waits for an admin to approve it before it can see anything.

If your team is one connected clinic with several staff, use clinic mode. If your devices spend days or weeks with no signal and change hands within a small trusted team, field mode is the honest choice.

Switching modes: the drain rule

The mode is switched in the Organization card under Settings, with "Switch to clinic mode" or "Switch to field mode". The server only accepts a switch to clinic mode from a signed-in administrator account, so the first-ever switch is done during cloud setup (SETUP.md section 4). The app asks twice before any switch, because the rule that matters is easy to skip:

Switching to clinic mode, the app asks

"Switch this organization to clinic mode?

Sync every field device to zero pending records first. The moment the mode flips, devices that have not signed in cannot push.

Staff will sign in with their own accounts, and an admin must approve each account before it can see anything."

Then a last check

"Last check before switching to clinic mode.

Has EVERY field device synced to zero pending records? A visit still waiting on a device that never signs in is stranded until an admin switches the mode back to field."

That is the drain rule: before flipping to clinic mode, bring every field device online, tap its sync chip, and confirm the Cloud sync card says "Nothing pending". A visit stranded on an unsynced device is not lost, but it cannot upload until an admin switches back to field mode, lets it drain, and switches forward again. Switching back warns just as loudly:

Switching back to field mode, the app asks

"Switch this organization back to field mode?

This reopens the shared-key surface: every device holding the project address and key can read and write records again without signing in. Anyone who ever had the key gets that access back too."

4. Clinic lists

The Clinic lists card under Settings fills the pick lists on the visit form. There are six lists, each a text box with its own save button: "Clinic or site names", "Clinicians", "Complaints", "Procedures", "Referral destinations", and "Patient flow stations (clinic mode board)".

The format is the same everywhere: one entry per line, and commas belong inside an entry. "Grace N., clinical officer" is one clinician, not two. On a cloud device, your organization's lists replace the local ones on the next sync, so edit them on an admin device and let sync carry them to everyone.

Two lists can never be empty. The app refuses with "You need at least one site. An empty list would block every save." and the same for clinicians. The other lists cannot be saved empty either.

Until real sites and clinicians are set, every visit is filed under the placeholders "Site A" and "Physician A", and the Settings screen shows a red warning: "This device is still filing records under placeholder names." Fix this before the first real clinic day; placeholder names are no use in a report.

Flow stations deserve extra care. The station list drives the clinic mode board, one station per line, in board order; the last station means done for the day. The app's own helper text explains the trap: station names are how visits point at a station, so renaming one strands today's visits under the old name. To rename mid-day, add the new name first and remove the old one after the day is done.

5. Form templates

The visit form itself is a template your organization owns: which forms are offered, their sections, and your own questions. Open the editor from the Form templates card under Settings, with "Open the template editor". The editor's own note applies to everything in it: "These belong to your organization. A change here reaches everyone on the next sync."

On a brand-new device that has not synced yet, the editor refuses to open for writing: "Your organization's form has not synced to this device yet. Editing is turned off until it arrives, because saving now would replace your organization's real form with an empty one." Sync the device, then come back. That guard protects the whole team; do not work around it.

The Forms card

Each form has an editable name box, an "On" checkbox, and three buttons: "Sections", "Duplicate", and "Delete".

  • Create: type a name in the "New form name" box and tap "Add form".
  • Duplicate: makes a copy named "name (copy)". Duplicating first is the safe way to experiment with a working form.
  • Rename: edit the name box directly. Every visit keeps the name of the form it was filed under, so old visits are not affected.
  • Turn on or off: the "On" checkbox decides whether the form is offered for new visits. With more than one form on, the visit form shows a "Form template" selector.
  • Delete: the app confirms, and the confirm says exactly what deleting keeps:

The delete confirm

"Delete the "name" form?

Visits already filed under it keep their answers and their template name. The form just stops being offered for new visits."

The editor never lets you strand the team without a visit form. It refuses to delete the last form ("At least one form must remain. Add another form before deleting this one.") and refuses to turn off the last enabled one ("At least one form must stay on, or there is no visit form to open. Turn another form on first."). If deleting a form would leave nothing on, the editor turns another form on for you and says so.

Sections

Tap "Sections" on a form to work on its layout. You can reorder sections with the up and down arrows, rename them in place, and hide the ones your clinic does not use with "Hide" and "Show". A renamed built-in section gets a "Reset name" button to go back to its original title. Two sections can never be hidden: Visit and Patient carry a disabled "Always shown" button, because every visit needs them.

"Add a section" creates your own section, and "Questions" opens its question list. Custom sections can be set to start collapsed on the visit form, unless they contain a required question; a collapsed section would hide an answer that Save demands, so the app locks that checkbox and says why.

Deleting a custom section confirms with the same promise as forms: "Answers already saved on existing records are kept, but will no longer appear on the form."

One thing is deliberately not in the template editor: the lists the built-in sections offer, like medications and lab tests, are edited on the Settings screen, not here.

Questions

Inside a custom section, each question has a label, a type, and a "Required" checkbox. The types are: Short text, Long text, Single choice, Multiple choice, Number, Scale (0-N), Yes / No, and Date. Choice questions get a "Choices" editor, one choice per line; scale questions get "Lowest" and "Highest" bounds.

Under every question the editor shows its field id, with the note "The field id is permanent; saved answers stay linked to it." That is why removing a question is safe for old records: "Answers already saved on existing records are kept, but this question will no longer appear."

6. Formulary

The Formulary card under Settings holds the medications offered on the visit form: a table of Medication, Dose, Unit, Category, and Controlled, with "Add medication" and "Save formulary" buttons.

One rule matters more than the rest. The card's own intro states it: "Edit carefully: saved prescriptions keep pointing at the same entry, so never reuse a row for a different drug - add a new row instead." Editing a row to become a different drug silently changes what old prescriptions appear to say. Add new rows; remove rows you no longer stock.

The formulary cannot be saved empty. After a save, changes appear when the visit form is next opened.

7. Lab tests and reference ranges

The Lab tests card defines the lab panel on the visit form: a table of Test, Type, Unit, On by default, and Ranges. A test's type is "Positive / negative" (POS and NEG buttons on the form) or "Number" (a number box with the unit as its placeholder). Saving replaces the whole panel for your organization, and the list cannot be saved empty.

Numeric tests get a "Ranges" button that opens the reference range editor. On a row that has not been saved yet the button is off, with the reason: "Save lab tests first, then set the reference ranges for this test."

Reference ranges: new results only

Ranges interpret a numeric value as it is entered, with a label and an optional color: Green (normal), Amber (caution), Red (critical), or Gray (neutral). The editor states the rule that governs everything here, and it is worth quoting in full:

The editor's standing notice

"Changing ranges affects new results only.

Visits already saved keep the interpretation that was recorded at the time; editing ranges never rewrites a recorded result. Only new results entered after this change use the new ranges."

Matching works top to bottom, first match wins. A value equal to "From (at least)" is inside the range; a value equal to "Up to (below)" is not, it belongs to the next range up. The editor warns about overlaps, gaps, and impossible ranges before you save, but still lets you save; read the warnings. Use the "Try a value" box at the bottom to see exactly what a new result would record before saving.

8. Diagnosis quick-picks and prescription presets

Both live in their own cards under Settings, and both belong to the organization: a change reaches everyone on the next sync.

Diagnosis quick-picks are the tap-to-add buttons under the Diagnosis box on the visit form; each tap appends to the diagnosis text. Prescription presets are one-tap bundles in the Medications section; applying one adds its medication lines and its treatment notes to the visit. Applying a preset only ever adds; it never removes rows a clinician already entered.

In both editors you can reorder entries, edit them, and choose between two very different actions:

  • Hide keeps the entry in your list but takes its button off the visit form. The tooltip says it plainly: "Hidden entries stay in the list but do not appear on the visit form." Hiding is reversible with "Show".
  • Remove deletes the entry from the list. Saved visits are never touched: "Diagnoses already saved on visits keep their text - only the quick-pick button goes away", and for presets, "Prescriptions already saved on visits are kept, and the formulary is not changed - only the one-tap preset goes away."

DH EMR ships with built-in defaults in both lists. You can remove them too, and the confirm adds a warning: "This is a built-in preset, so once saved it stays removed for your organization after sync." If you only want a cleaner form, hide instead of removing; the app even says so when you try to save an empty list: "The diagnosis quick-picks cannot be saved empty. Hide entries instead if you do not want them on the visit form."

When building a prescription preset, the editor checks every medication line and tells you what it will record. A drug that is not in your formulary is allowed, but flagged: "Not in the formulary - prescriptions from this line record no dispensing quantity." Fix the formulary first if you want quantities.

9. Staff accounts (clinic mode)

In clinic mode, admins get a Staff tab. Its card says what it does: "Approve new accounts, set station roles, and revoke access. A new account can see nothing until it is approved here. Changes are enforced by the server: a device that is offline keeps its last confirmed access and is cut off the moment it reconnects."

Staff create their own accounts from the sign-in screen on any device connected to your organization. This is safe because signing up grants nothing: every new account starts pending, sees no data, and waits on your list. There is no rush to approve.

For each account you can:

  • Set a station role: reception, nurse, provider, or pharmacy. On the flow board, the signed-in role's matching station is tagged "your station".
  • Approve a pending account, after which it can sign in and work.
  • Revoke an active account. The confirm is honest about timing and data: "They are locked out the next time their device talks to the server. Nothing they recorded is deleted, and you can restore them here later."
  • Restore a revoked account.
  • Make admin or Remove admin. The confirm spells out what that means: "Admins approve and revoke accounts, edit the organization's lists and formulary, and can switch the organization's mode."

The last-admin rule: the app and the server both refuse to let the only administrator revoke or demote themselves: "You are the only administrator. Make someone else an admin first." Keep at least two admins so a lost password never locks the organization.

Revoking never deletes anything: visits an account recorded stay in the organization. And if you do lock yourselves out entirely, or the sole admin forgets their password, the recovery steps live in SETUP.md's recovery playbook, using the project dashboard and SQL editor. Password reset emails are not reliable on most clinic projects; the sign-in screen itself tells staff: "Forgot your password? Your administrator can set up a fresh account for you - password reset emails are not reliable on most clinic projects."

10. Your device fleet

A device registers itself with your cloud the first time it connects: in the setup wizard's cloud path, or later under Settings with "Connect this device to a cloud". Its name, role, and last sync time land in your project's devices table.

  • Renaming is safe. The This device card's "Rename this device" changes only the label. The card says why that matters: "Renaming keeps this device's identity: records it has already filed stay its own." A rename never re-registers, never mints a new identity, and never orphans records.
  • Review the fleet regularly. SETUP.md's operator quick reference has a one-query fleet listing for the SQL editor: recognize every row; revoke strangers.
  • Revoking a lost or stolen device is done from the SQL editor, with the one-line update in SETUP.md. Records the device already pushed are kept. The app can never un-revoke a device; that also lives only in the SQL editor, on purpose.
  • Changing a device's role (standard to admin, or back) is done in the cloud's devices table; the device adopts the cloud's role on its next sync.

To replace a device, follow the Moving to a new device card under Settings: download a backup on the old device, connect the new device to the same cloud project, restore the backup, and check the record count matches before wiping the old device.

Honest limit: revoking a device does nothing to the data already on a lost device, and that data is not encrypted at rest. Treat a lost device as a disclosure, not just an access problem.

11. Backups and restore

The Backup and restore card under Settings explains what a backup is: "A backup is a single file holding every record on this device plus your form and preset settings. It never contains your cloud key or device identity. Take one at the end of each clinic day - it is the safety net if a device is lost, wiped, or replaced." As the admin, make that habit stick: one tap on "Download backup", one file somewhere safe.

Restoring merges; it never wipes. The card's own footer is the rule: "Restoring merges: nothing already on this device is lost, and where the same record exists in both the more recently saved version wins." So a restore cannot undo newer work.

Settings restore is separate and opt-in. After confirming the records restore, the app asks a second question:

The settings restore confirm

"Also restore the settings from this file?

That replaces this device's form layout, sites, providers and formulary with the ones in the backup. If this is an admin device those settings go out to the whole team on the next sync.

Choose Cancel to restore records only. That is almost always what you want."

Take that last line seriously, especially on an admin device: restoring old settings from a months-old backup and syncing would roll the whole organization's forms back. Tap Cancel unless you are deliberately restoring configuration.

If you are moving records across from an old cloud project, use the separate Moving from another cloud project card with "Import records from a file". Export from the old project as JSON, not CSV; CSV flattens lab results and medication lists into text that cannot be read back reliably.

12. The demo

The demo is a fictional clinic with sample patients, running entirely in the browser. Its banner states the laws: "A fictional clinic with sample patients. Everything stays in this browser and never syncs anywhere." It refuses every cloud connection on purpose, so nothing done in the demo can ever touch your organization's records or settings.

That makes it the right place to rehearse. Try the template editor, build a preset, break things freely. "Reset Demo" in the banner puts the original sample patients back.

13. Honest limits

  • Field mode's key is the whole fence. Every device shares one key, the database cannot tell devices apart, and anyone holding the key can read everything. Revocation stops an honest revoked device, not a determined person who has the key. Clinic mode, with per-user accounts, is the fix.
  • An admin can reopen that fence. Switching a clinic mode organization back to field mode reopens the shared-key surface for everyone who ever had the key. It exists as the recovery path for stranded field records, and the app confirms it loudly.
  • A lost device keeps its data. Revoking does nothing to records already on the device, and they are not encrypted at rest.
  • DH EMR is not a certified EHR and is not HIPAA-compliant. It must not be used where a certified EHR is required. It is intended for global-health use outside the US.
