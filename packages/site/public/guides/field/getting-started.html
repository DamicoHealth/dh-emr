Getting started with DH EMR Field

DH EMR Field is for entering visits from paper charts after clinic. This guide takes one device from blank to its first saved visit and its first backup. It covers both ways of running Field: one device on its own, or several devices that sync through your organization's own cloud.

Two words the app uses everywhere: a visit is one patient seen on one day, and the patient number is the short code the app creates for each patient from the name and date of birth. You never type it.

1. Who Field is for

Field is the paper-chart product. The clinic runs on paper during the day. Afterward, at the end of the day or the next morning, someone opens Field and enters each chart as a visit. Everything is saved on the device. No connection is needed to enter or read a visit.

There are two ways to run it:

  • One device on its own. Records stay on that device and are never sent anywhere. The backup file you download is the only other copy.
  • Several devices, one cloud. Each device enters visits on its own and syncs them to a cloud project that your organization owns, whenever there is signal. After a sync, every device holds every visit. There are no accounts: every device uses the same project address and project key, which your admin gives you. The cloud sync guide explains how an admin sets that up.

Field is also the fallback for an organization that runs DH EMR Clinic. When the Clinic backend is down, staff chart on paper and enter the day's charts in Field afterward. The admin guide explains what that does and does not give you.

What Field does not have

There are no accounts and no sign-in; the device is the identity. There are no staff roles and no patient-flow board. Those belong to DH EMR Clinic, which is a separate product. There is no switch between the two products, and there is no way to move records from Field into Clinic today.

2. What you need

  • A device with a modern browser: a tablet, a laptop, or a phone. Open the Field app. On most tablets and phones the browser can add it to the home screen so it opens like an app.
  • Only for the cloud path: the project address and project key. Your admin gets both from the organization's Supabase project. You do not need them for a device on its own.
  • A few paper charts to enter.

3. The setup wizard

The first time the app opens on a device it shows a short wizard headed Set up this device. The app's own words: "This takes about a minute and only happens once. You can change any of it later under Settings." One choice is harder to change than the rest, whether the device is an admin device, and this guide says so below.

The wizard shows until setup is finished. If the app is closed part way through, it starts again from the first step next time. Nothing is stored until the last step succeeds, so a wrong key or a typo cannot leave the device half set up.

The first step is a choice between two buttons:

  • Connect to our clinic cloud: "Records sync between every device on the team. Needs the project address and key from your admin."
  • Use this device on its own: "Records stay on this device and are never sent anywhere. Take a backup at the end of each clinic day."

Path 1: use this device on its own

Tap Use this device on its own. The wizard goes straight to naming the device. There is nothing to connect.

Path 2: connect to our clinic cloud

Tap Connect to our clinic cloud. The next step is headed Connect to your cloud. It says where the values come from: "Your admin gets both of these from the Supabase project, under Settings then API Keys." There are two boxes:

  • Project URL: looks like https://yourproject.supabase.co
  • Project key: a long string that starts with sb_publishable_, or the long legacy anon key

The key rule, in the app's own words: "Use the Publishable key, or the legacy anon key. Never a Secret or service_role key: those bypass every database security rule and must not leave the office." The app refuses server keys. If you paste one you get an error, not a connection. Ask your admin for the publishable key.

Tap Check and continue. The button reads "Checking…" while the app contacts the project and checks that its tables are really there. If something is wrong, a plain message says what:

The wizard saysWhat to do
"That does not look like a Supabase project URL. It should look like https://yourproject.supabase.co"Check the address with your admin. It must start with https:// and end in .supabase.co.
"Paste the project anon key."The key box is empty.
"That is a server key (service_role or sb_secret). It bypasses every database security rule and must never go on a field device. Use the Publishable key, or the legacy anon key."You were given the wrong kind of key. Ask your admin for the publishable key. Do not try to work around this.
"Could not reach the project tables:" followed by the reason the project gaveThe project answered but something is wrong with it. Show the reason to your admin.
"Connected, but the records table was not found. Run the setup SQL on this Supabase project first."The project exists but has not been set up yet. Your admin needs to finish the cloud sync setup.
"Could not reach that project. Check the device is online and the URL is right. (...)"The device is offline, or the address is wrong. Get signal and try again.

Back returns to the first step. After the check passes, the cloud path continues to the same naming and clinic-lists steps as the other path.

Naming the device, both paths

The step headed Name this device asks for two things:

  • Device name. The app says why it matters: "The name shows up in your device list and on the records this device files, so make it something you can recognise: "iPad 2 - triage", "Grace's tablet"." A blank name is refused: "Give this device a name so it can be told apart from the others."
  • What is this device allowed to do? A list with two choices: Enter and view records (most devices) and Also change the form and clinic settings for everyone. The first choice makes a standard device. The second makes an admin device, which can change the clinic lists, the formulary, the lab tests, the presets and the visit form for the whole team. Most devices should be standard. One or two admin devices per team is plenty.

Under those, the wizard says which kind of device this is: "This device is offline only. Nothing it records leaves the device." on the first path, or "This device is connected to your cloud. Records sync automatically." on the cloud path.

Choose the admin question carefully. There is no control in the app to change it later. On a cloud device, the admin can change a device's role in the project's device list, and the device picks it up on its next sync; the admin guide explains how. On a device on its own, the choice stands.

4. Clinic lists, and why empty lists are refused

The last step is headed Where is this device working?. The app explains: "These fill the Site and Provider lists on the visit form. Without them every record is filed under the placeholder "Site A", which is no use in a report. One per line, and you can change them later under Settings." There are two boxes:

  • Clinic or site names: the places where you see patients, one per line, for example "Kabale Community Clinic" and "Mobile Unit A"
  • Clinicians working on this device: the people who will be recorded as the provider on visits, one per line, for example "Dr. A. Mensah" and "Grace N., clinical officer"

Two rules, both written on the step itself:

  • One entry per line. Commas belong inside an entry: "Grace N., clinical officer" is one clinician, not two. The app never splits on commas.
  • Both lists need at least one entry. The step says: "Both lists are needed to finish: a device with an empty list cannot save a visit." If you try to finish with a box empty, the wizard refuses: "You need at least one site. An empty list would block every save." and the same for clinicians.

Why the refusal? Every visit must have a site. If the site list were empty, the visit form could never be completed, and the device would be set up but useless. The wizard would rather stop you here than let that happen.

On the cloud path the step adds one line: "If your organization has already set these up in the cloud, its list replaces these on the first sync." Enter something sensible anyway, so the device works before that first sync.

Tap Start using the app. The button reads "Finishing…" while the device is registered. On the cloud path, if the project refuses at this moment, the wizard says "Could not finish setup:" with the reason. Nothing was stored; get signal and try again.

Setup is done. If you entered placeholder names to get through setup, Settings will show a red warning until real sites and clinicians are set. The admin guide covers the Clinic lists card.

5. Your first visit, end to end

The app has four tabs: Visits, New visit, Analytics and Settings. On a phone they sit at the bottom of the screen; on a tablet or computer they are in the top bar. Take one paper chart and enter it:

  1. Tap New visit. A panel titled "New visit" slides in. The + New visit button on the Visits tab does the same thing. Under the title it says "Patient number generates from name + date of birth".
  2. In the Visit section, pick the Site, set the Date, and pick the Provider. Site and Date are required. The date starts as today. For a paper chart, change it to the date written on the chart, the day the patient was seen, not the day you are typing. The app refuses a date in the future.
  3. In the Patient section, enter the Given name and Family name, tap M or F for Sex, and type the Date of birth as DD/MM/YYYY. If the chart has no date of birth, tick Estimate from age next to "Date of birth unknown" and type an Estimated age in years instead. Phone is optional.
  4. Watch the Patient number box. It is read-only and fills in by itself once the name and date of birth are entered. It is two letters of the given name, two letters of the family name, and the date of birth. A patient named Amara Nakato born on 12 April 1991 becomes AMNA12041991. The same patient gets the same number every time, and if two different patients would collide the app adds a letter to keep them apart. Both names need at least two letters.
  5. Fill in the rest of the form from the chart: Vitals, History, Chief Concern, Labs, Diagnosis, Medications. The sections Procedures, Referral, Imaging, Surgery and Notes start closed; tap a section header to open it. Enter what is on the chart and leave the rest empty. The user guide explains every field.
  6. Save. There are two save buttons at the bottom of the panel:
    • Save & next patient files the visit and keeps the form open for the next chart. Site, Date and Provider stay filled; everything else clears. A green note confirms it, for example "Saved Amara Nakato (AMNA12041991). Ready for the next patient." This is the button for a pile of charts.
    • Save files the visit and closes the panel. Use it for the last chart of the pile.

If a required field is missing, the visit is not saved. A red summary appears, for example "Check 2 fields", listing each problem in plain words such as "Family name is required." The form jumps to the first one. Fix the fields and save again. Nothing is lost.

Cancel closes the form. If you have typed anything, the app first asks "Discard this visit? Anything you have entered will be lost." Tap OK to discard, or Cancel to keep working. Tapping outside the panel does nothing, on purpose, so a stray touch cannot lose a visit.

Saved visits appear on the Visits tab, one card per patient. The four counts at the top of that tab, Visits, Patients, Today and Pediatric (<18), cover everything on the device. Tap a card to open the patient's chart.

6. Where your records live

Every visit is saved on the device itself, always. Saving never needs a connection. On a cloud device, visits also upload to your organization's project whenever there is signal, and visits from the other devices download.

The chip at the right of the top bar shows where syncing stands. On a device on its own it reads Offline only and does nothing when tapped. On a cloud device, tapping it runs a sync by hand, and while records are waiting to upload it shows a count like "3 pending" (on a phone the count is in Settings instead, on the Waiting to sync row of the Cloud sync card).

Chip saysWhat it means
Offline onlyCloud sync is off for this device. Records stay on the device.
ConnectedThe cloud is set up but nothing has synced yet this session.
OfflineNo connection right now. Everything is saved on the device and syncs when you reconnect. This is normal.
SyncingRecords are being sent and received right now.
SyncedAll records are backed up to your cloud.
Sync errorThe last sync failed. Tap to retry, or check the connection. Records are still safe on the device.

7. Take a backup, daily

Open Settings, find the Backup and restore card, and tap Download backup. The card explains what you get: "A backup is a single file holding every record on this device plus your form and preset settings. It never contains your cloud key or device identity. Take one at the end of each clinic day - it is the safety net if a device is lost, wiped, or replaced."

The file is named dh-emr-backup followed by the date, for example dh-emr-backup-2026-10-06.json, and the app confirms with "Backup downloaded with 12 records. Keep it somewhere safe." Move the file off the device: a laptop, a USB stick, a shared drive folder.

Do this at the end of every day of entry. On a device on its own, the backup file is the only copy of your records that exists outside the device. If the device is lost, wiped or broken, the backup is the difference between losing an afternoon and losing a year. Cloud devices should back up too; it is the safety net for records that have not synced yet.

Restoring is on the same card, with Restore from a backup. It merges: "nothing already on this device is lost, and where the same record exists in both the more recently saved version wins."
