Cloud sync setup

For the admin who wants several DH EMR Field devices to share one set of records. This guide stands up a cloud project that your organization owns, connects the devices to it, and explains what that does and does not protect. It takes about fifteen minutes and needs no command line. A single device on its own does not need any of this.

1. What cloud sync gives you

Each Field device enters visits on its own, offline. With cloud sync, every device also uploads its visits to one project whenever it has signal, and downloads the visits the other devices entered. After a sync, every device holds every visit, and an admin device's lists, formulary, lab tests, presets and forms reach the whole team.

The project is a Supabase project that your organization creates and owns. Damico Health hosts nothing and sees nothing: there is no central server, no account with us, and no subscription. The records live on your devices and in your project.

There are no user accounts in Field. Every device uses the same project address and the same project key. That is simple to set up and it is also the main limit, explained plainly in section 12. Read it before you decide.

2. Before you start

  • A Supabase account, at supabase.com. The free tier is enough for a small fleet.
  • The two SQL files that set up and check the project: setup.sql and verify.sql. They live in the supabase folder of the DH EMR source code, next to the full step-by-step in SETUP.md. Until they are published on this site, that is where they live.
  • Fifteen minutes, and a browser on a computer. The dashboard is easier on a large screen.

3. Create the project

  1. On supabase.com, choose New project. Any name. Pick the region closest to the clinic.
  2. Generate a strong database password and store it in a password manager. It is rarely needed again.
  3. Wait for the project to finish provisioning.

4. Run the schema

  1. In the left sidebar, open SQL Editor, then New query.
  2. Paste the entire contents of setup.sql and click Run.
  3. It is safe to run twice; re-running is the documented upgrade path.
  4. Recommended: paste and run verify.sql next. Every row of its output must say PASS. It changes nothing; it ends by rolling itself back.

If you are upgrading a project that is already in use, run it after clinic hours. The run briefly locks the records table, and a device syncing during those seconds shows a sync error, retries, and succeeds afterward. Nothing is lost either way; it is just alarming to watch mid-clinic.

5. Get the app credentials

  1. Project URL: Project Settings, then Data API. It is also shown in the Connect dialog at the top of the dashboard. It looks like https://yourproject.supabase.co.
  2. Publishable key (sb_publishable_...): Project Settings, then API Keys.

Those two values are what every device enters. Write them down for the people setting up devices.

The key rule. Devices get the publishable key, or the legacy anon key, and nothing else. Never put the sb_secret_... key or a legacy service_role key on any device, in any chat, or in the app. It bypasses every security rule. The app refuses keys that look like it, on purpose, with the message: "That is a server key (service_role or sb_secret). It bypasses every database security rule and must never go on a field device. Use the Publishable key, or the legacy anon key."

That is the whole setup for Field. There are no accounts to create and no sign-in to enable.

6. Connect each device

There are two ways to connect a device, and they end in the same place.

A new device: the setup wizard

On the first screen, tap Connect to our clinic cloud. The step headed Connect to your cloud asks for the Project URL and the Project key. Tap Check and continue; the app contacts the project and checks that its tables exist before letting you go on. Then name the device, choose whether it is an admin device, enter the clinic lists, and tap Start using the app. Getting started walks through every step and every error message.

A device already in use

Open Settings, find the Cloud sync card, and tap Connect this device to a cloud. A form opens with Project address (from your admin) and Project key. Tap Verify and connect. On success the app says: "Connected and registered. Records on this device will upload on the next sync." Every visit already on the device uploads with that first sync. The Cloud sync card updates at once; close and reopen the app so the chip in the top bar does too.

If the check fails, the message says why. "That URL or key does not look right. The URL should look like https://yourproject.supabase.co" means a typo. "Could not reach the project tables:" followed by a reason, or "Connected, but the records table was not found. Run the setup SQL on that project first." means section 4 was skipped.

Connecting registers the device in the project's devices table with the name and role chosen at setup. The project's security rules only accept records from devices in that table.

7. Verify with one test visit

  1. On a connected device, enter one test visit and save it.
  2. Tap the chip in the top bar, or Sync now on the Cloud sync card. The card says "Sync finished. 1 record uploaded. Nothing is waiting."
  3. In the dashboard, open Table Editor, then records. One row is there.
  4. Delete the test visit in the app, from the patient's chart, not in the dashboard. Deleting in the app marks the record deleted on every device; rows are never hard-deleted, by design.
  5. Optional but worth it: enter a visit on a second device, sync both, and check that each device shows the other's visit on its Visits tab.

8. Day to day

Sync runs when a device is online, and anyone can run it by hand by tapping the chip or Sync now. The Cloud sync card shows the Project, the Status, and Waiting to sync ("Nothing pending", or the number of records). The user guide explains every chip state.

If a sync cannot upload everything, the app says so plainly rather than pretending: "NOT backed up." followed by how many records are still waiting, the reason, and "Take a backup before wiping or handing on this device." Treat that as an instruction.

Settings that belong to the organization, the clinic lists, formulary, lab tests, reference ranges, presets and form templates, are edited on an admin device and reach every other device on its next sync. The Form templates card says so: "These belong to your organization; a change reaches everyone on the next sync." The quick-pick, preset and reference range cards carry the same line in their own words. On a standard device the organization's lists replace the local ones at the next sync, so edit on the admin device only.

Change cloud project on the Cloud sync card opens the same connect form for pointing the device at a different project. Records already on the device upload to the new project on the next sync.

9. The device fleet

Everything here is done in the dashboard's SQL Editor. The app itself cannot revoke, un-revoke, or change a device's role, on purpose, so that a stolen device cannot do any of it either.

List every device

Recognize every row. Revoke strangers.

SELECT id, name, role, created_at, last_sync_at,
       CASE WHEN revoked_at IS NULL THEN 'active' ELSE 'REVOKED' END AS status
FROM devices ORDER BY last_sync_at DESC NULLS LAST;

Revoke a lost or stolen device

Records it already pushed are kept.

UPDATE devices SET revoked_at = now() WHERE id = '<device id>';

Un-revoke a device

UPDATE devices SET revoked_at = NULL WHERE id = '<device id>';

Change a device's role

The role in the cloud is authoritative. Set it to admin or standard and the device adopts it on its next sync; there is no control in the app for this.

UPDATE devices SET role = 'admin' WHERE id = '<device id>';

Sanity check the row counts

Run this before and after any migration; the numbers must match.

SELECT (SELECT count(*) FROM records) AS records,
       (SELECT count(*) FROM records WHERE deleted IS TRUE) AS deleted_records,
       (SELECT count(*) FROM devices) AS devices,
       (SELECT count(*) FROM config) AS config_rows,
       (SELECT max(saved_at) FROM records) AS newest_record;

Renaming a device is done in the app, on the This device card with Rename this device, and is always safe: it changes the label only and never re-registers the device. The admin guide covers renaming and replacing devices.

10. Free-tier pausing

Supabase pauses free-tier projects after about a week with no traffic, and a project paused long enough (around 90 days) can stop being restorable in place. A team that syncs twice a year and never opens the dashboard can silently lose its cloud copy this way.

If your usage is episodic, do one of these: upgrade the project to a paid tier, or put a calendar reminder to open the dashboard monthly and click Restore if prompted. And always keep device backups. The app's backup file is the true archive; the cloud is a convenience copy for the devices, not the organization's only copy.

11. Moving to a new project

If you ever replace the project, for example after a key has leaked, there are two steps for each device. First, point it at the new project with Change cloud project; records already on the device upload there on the next sync. Second, if some records exist only in the old project and on no device, export them from the old project as JSON and bring them in through the Moving from another cloud project card with Import records from a file. The card's warning matters: "Export as JSON, not CSV. CSV flattens lab results and medication lists into text and they cannot be read back reliably." The admin guide covers the import.

12. The honest limit of a shared key

Every Field device shares one key. The database cannot tell devices apart, so anyone holding the key can read everything in the project and write to it. The key is the whole fence.

  • Revoking stops an honest device, not a determined person. The revocation switch in section 9 stops a revoked device from syncing. It does not stop someone who copied the key into another tool. If the key has leaked, the only real fix is a new project with a new key, and reconnecting every device.
  • There is no record of who entered what. A visit carries the device that filed it and the provider picked on the form. Nobody signed in, so nothing proves who held the device.
  • A lost device keeps its data. Revoking does nothing to the records already on it, and they are not encrypted at rest. Treat a lost device as a disclosure.
  • If you need accounts, you need DH EMR Clinic. Clinic gives every staff member their own sign-in and roles. It is a separate product with its own project setup, and there is no path from a Field organization into Clinic today. Choose with that in mind.

For a small, trusted team whose devices spend days without signal, the shared key is an honest trade. Make it as safe as it can be: give the key to the people setting up devices and nobody else, review the fleet listing now and then, and keep backups.
